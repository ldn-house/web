# Apex launch checklist

This is preparation only. Leave the launch PR in draft until the live-power privacy decision is settled. Neither `robots.txt` nor `noindex` protects readings from access. Merging to `main` automatically deploys production.

1. **Resolve privacy, then inspect the zone before merging.** Confirm `ldn.house` is an active Cloudflare zone in the deployment account. Check DNS and Workers & Pages → Domains & Routes for `ldn.house` and `www.ldn.house`: no conflicting A/AAAA/CNAME records or custom-domain bindings to another service. Check Page Rules, Single/Bulk Redirects and wildcard Worker routes for apex-to-www loops or rules that intercept these hosts. Review restrictive CAA records if present. Preserve all MX, mail-related TXT and mail-host records; an MX record itself is not a web-route conflict, but an MX target of the apex would need attention before making the apex a web-only Worker origin. Leave Grafana's `dashboard.ldn.house` records, routes and rules alone. Do not create a wildcard route or zone-wide redirect.
2. **Confirm the existing GitHub Actions token's resource scopes.** `CLOUDFLARE_ACCOUNT_ID` must own the zone and Worker. The documented legacy permissions—account Workers Scripts edit and D1 edit, plus zone Workers Routes edit covering `ldn.house`—are sufficient for this custom-domain deployment; no additional DNS edit permission is required for Cloudflare-managed DNS creation. Keep account coverage for creating/deleting PR Workers and D1 databases. Do not replace this with access restricted to the existing production Worker, which would break preview provisioning. If the current secret already has these scopes, no token change is needed.
3. **Merge only when ready to publish.** There is no manual DNS record or redirect rule to create. The production workflow migrates D1 and deploys the three exact custom domains from `wrangler.jsonc`; Cloudflare creates the apex/www DNS records and certificates. The pinned Wrangler 4.127.0 sets `override_existing_origin` and `override_existing_dns_record` in noninteractive runs, so do not rely on CI to stop for conflicts. Recheck step 1 immediately before merging. Do not manually deploy this branch or attach the apex ahead of the privacy decision.
4. **Verify the production workflow and domain activation.** Wait for DNS and TLS activation, then check `https://ldn.house/` serves the app; `https://www.ldn.house/not-a-page?check=launch` returns 301 with `Location: https://ldn.house/not-a-page?check=launch`; the same redirect applies to `/favicon.svg` and `/share.png`; the target missing path returns 404. Confirm the favicon, share image, canonical/meta tags and apex `robots.txt`. Confirm `preview.ldn.house` still serves the app and Grafana's existing hostname still behaves as before. Social scrapers cannot fetch the apex share image until launch; check an actual shared link then.
5. **Keep the normal PR-preview lifecycle.** Draft PRs run checks, provision an isolated Worker/database, deploy on `workers.dev`, seed the scrubbed fixture and comment the URL. `previewConfig()` strips every production route and cron trigger. Closing the PR deletes only its preview resources. No preview-workflow or Cloudflare-rule change is needed for the apex.

## Evidence and limits

Read-only checks on 2026-10-19 found no public A, AAAA, CNAME, MX or CAA answers for `ldn.house` or `www.ldn.house`; `preview.ldn.house` and `dashboard.ldn.house` returned Cloudflare A/AAAA answers. Public DNS does not expose the underlying proxied records or prove that zone rules are absent. No Cloudflare configuration was changed during preparation. A GET of `/zones?name=ldn.house` using the available local Wrangler login returned HTTP 403 / `9109 Invalid access token` (expired login). The GitHub Actions secret cannot be read back. Exact token scopes, private zone records, other custom-domain bindings and redirect/Page Rules therefore remain manual checks, not verified absences.

[Cloudflare's custom-domain guide](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) documents automatic DNS/certificates, the active-zone requirement, CNAME conflicts and exact-host matching. [Workers authorization](https://developers.cloudflare.com/workers/authorization/workers/) requires Worker edit access plus Workers Routes write for each affected zone; legacy permissions continue to work. The [domain attachment API](https://developers.cloudflare.com/api/resources/workers/subresources/domains/methods/update/) lists Workers Scripts write, not DNS write. DNS read and rules read access would help audit conflicts but are distinct from deployment permissions.

The `www` redirect is in the Worker so code, domains and redirect ship together through the existing workflow and can be exercised in local workerd and reviewed in one diff. A Cloudflare redirect rule could avoid Worker invocations, but would add separately managed configuration and permissions. `assets.run_worker_first` ensures static assets also redirect and receive the host-specific indexing policy; this makes asset requests invoke the Worker too. The share card is a static 1200×630 PNG with no live or historical readings; its editable source is `public/share.svg` (`rsvg-convert public/share.svg -o public/share.png`). No Octopus endpoints, polling intervals, retries or cache lifetimes change; both production hostnames share one refresh gate, rather than creating a deployment per hostname.

# Apex launch checklist

Merging this PR to `main` publishes `ldn.house` and `www.ldn.house` through GitHub Actions. Keep `preview.ldn.house` serving the same gated site in parallel; both production hosts share the Worker and D1, but browser enrolment is separate on each host. `dashboard.ldn.house` remains independent.

1. **Zone audit complete (2026-10-20).** The coordinating thread inspected the Cloudflare API read-only: `ldn.house` is active on the Free plan, with no DNS records at apex/www and no MX or TXT records. There are no conflicting records or email records to preserve. The only Worker custom domain is `preview.ldn.house` on service `ldn-house` (production), with its managed, read-only AAAA record; there are no Worker routes, Page Rules or Single Redirect rules. Wrangler can create apex/www without conflicts. Preserve the unrelated proxied Tunnel CNAMEs at `dashboard`, `control`, `status` and `uptime`. The zone-wide **Bots** rule blocks BY, IR, IQ, RU and KP and will also apply to the apex; leave it unchanged. Managed rulesets are the defaults: normalization, the Free managed ruleset and DDoS.
2. **Confirm deployment-token coverage.** The existing `CLOUDFLARE_ACCOUNT_ID` must own the Worker and zone. Account Workers Scripts edit and D1 edit, plus zone Workers Routes edit covering `ldn.house`, suffice for custom-domain deployment: no extra DNS edit permission or manually created DNS record is required. Retain account coverage for creating/deleting PR Workers and D1 databases. If the current secret has those scopes, leave it unchanged. The Actions secret cannot be read back locally; the zone audit does not establish that secret's exact permission/resource scopes.
3. **Prepare Home Assistant's host changes.** Once apex HTTPS is active, Cameron must change both `rest_command` URLs to `https://ldn.house/api/home/confirm` and `https://ldn.house/api/home/codes`, and update the approval notification text to name/link `ldn.house`. Keep the bearer token and cookie signing secret unchanged. `HOME_ASSISTANT_WEBHOOK_URL` is the local LAN webhook address used by the browser and stays unchanged. Send these POST requests directly to the apex, not `www`: a 301 can turn a POST into a GET. Calls to preview remain valid during transition because the Worker and D1 are shared; links minted by `/api/home/codes` use the origin that received that request.
4. **Merge and monitor the production deployment.** Cameron can squash-merge after the required `check` passes. Actions migrates D1, then deploys the three exact custom domains in `wrangler.jsonc`; Cloudflare creates apex/www DNS records and certificates. No redirect rule needs adding. The pinned Wrangler 4.127.0 sets `override_existing_origin` and `override_existing_dns_record` in noninteractive runs, so if zone configuration changes after the audit, recheck conflicts before merging rather than relying on CI to reject them. Do not attach domains or deploy this branch manually.
5. **Verify activation, then apply the prepared HA changes.** Wait for DNS/TLS, check the apex page, favicon, share card, canonical/social tags and `robots.txt`. Verify `https://www.ldn.house/not-a-page?check=launch` returns 301 to the same path/query at HTTPS apex, and the target returns the branded 404. Check www asset URLs and an enrolment GET link preserve path/query too. Confirm named preview still serves the gated app and Grafana behaves as before. Apply step 3, then exercise browser approval and a newly minted one-time link on the apex. The LAN webhook and real household approval must be checked from home; local/PR simulations cannot establish them.
6. **Re-enrol devices on the apex.** `__Host-ldn-home` and `__Host-ldn-enrol` have `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax` and no `Domain`. Existing preview cookies do not transfer: enrol each browser/device again on `ldn.house`. Verify an unenrolled browser sees only usage through yesterday, with no live watts or same-day data in HTML/hydration, `/_server` or `/api/live-power`; prices stay public. Verify an enrolled browser sees today's usage and live data. `?as=home`/`?as=outsider` and the tree season’s `?at=` date simulation are for localhost and isolated PR previews only and must have no effect on either production host, including after a www redirect.
7. **Keep preview available with independent enrolment.** Existing preview cookies remain usable until expiry/revocation; a device using both hosts must enrol on each. For a new preview enrolment, use that host's footer or mint a separate link via its `/api/home/codes` endpoint. Codes are single-use in the shared database, so do not reuse one link for both hosts. Browser POSTs remain same-origin; do not broaden CSRF checks or cookie domains. Home Assistant can confirm a pending preview enrolment through the apex callback because both hosts share D1. Named preview and PR previews remain excluded from indexing; crawler hints are not access controls.
8. **Keep the PR-preview lifecycle unchanged.** Draft and ready PRs run checks, create an isolated Worker/database, migrate, deploy on `workers.dev`, seed the scrubbed fixture (including the existing Cloudflare 1042 retry) and comment the URL. `previewConfig()` removes production routes and cron triggers. Closing the PR deletes only its preview resources. Check an actual apex shared link after launch, when social scrapers can fetch its static image.

## Host compatibility

Visitor context is request-local. Browser enrolment requests and form actions are relative, one-time links use the minting request's origin, and CSRF checks compare the browser origin to the current request origin. The www redirect runs before enrolment handling: a GET link reaches the apex before its form is rendered, so its subsequent POST is same-origin and the code is not consumed by the redirect. No home-gate code assumes `preview.ldn.house`; host-specific cookie scope is intentional.

## Evidence and limits

The zone findings above come from the coordinating thread's read-only Cloudflare API inspection on 2026-10-20. They replace the earlier public-DNS-only check and unverified zone/rule items. No production Cloudflare configuration was changed during preparation; the existing Actions workflow deployed only isolated PR-preview resources. Exact GitHub Actions token scopes remain an owner-side check because the stored secret cannot be read back. Real apex DNS/TLS activation and household LAN approval are verified after launch.

[Cloudflare's custom-domain guide](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) documents automatic DNS/certificates, the active-zone requirement, CNAME conflicts and exact-host matching. [Workers authorization](https://developers.cloudflare.com/workers/authorization/workers/) requires Worker edit access plus Workers Routes write for each affected zone; legacy permissions continue to work. The [domain attachment API](https://developers.cloudflare.com/api/resources/workers/subresources/domains/methods/update/) lists Workers Scripts write, not DNS write. DNS read and rules read permissions used for the audit are distinct from deployment permissions.

The `www` redirect is in the Worker so code, domains and redirect ship together through the existing workflow and can be exercised in local workerd and reviewed in one diff. A Cloudflare redirect rule could avoid Worker invocations, but would add separately managed configuration and permissions. `assets.run_worker_first` ensures static assets also redirect and receive the host-specific indexing policy; this makes asset requests invoke the Worker too. The share card is a static 1200×630 PNG with no live or historical readings; its editable source is `public/share.svg` (`rsvg-convert public/share.svg -o public/share.png`). No Octopus endpoints, polling intervals, retries or cache lifetimes change; both production hostnames share one refresh gate, rather than creating a deployment per hostname.

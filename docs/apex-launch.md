# Apex launch checklist

This is preparation only. The launch depends on [privacy PR #26](https://github.com/ldn-house/web/pull/26), which is open with an independent security review in progress. Leave the launch PR in draft until that review is resolved, #26 is merged and its rollout is verified. Neither `robots.txt` nor `noindex` protects readings from access. Merging this launch PR to `main` automatically publishes the apex.

1. **Complete the privacy prerequisite before launch.** Before #26 merges, confirm the house is not behind Hyperoptic CGNAT: check the router WAN address against the public address Home Assistant reports. Set `HOME_REPORT_TOKEN` and `HOME_COOKIE_SECRET` on the production Worker and configure Home Assistant using #26’s instructions, initially reporting to `https://preview.ldn.house/api/home/address`. Wait for the independent security review and any resulting changes before merging #26. After its merge, nobody initially counts as home until Home Assistant reports. Confirm successful reports and both home and outsider views; a report becomes stale after 15 minutes, while a valid signed home cookie lasts 30 days. These setup actions are manual prerequisites, not performed by this launch PR.
2. **Integrate and revalidate the merged privacy change.** After #26 lands, update this launch branch from `main` and resolve the shared `src/worker.ts` and README changes without dropping the visitor context, home-report endpoint or privacy response headers. Re-run the production workerd checks on the combined result: outsiders have no live watts, last-hour average or usage after the London midnight that began today, in SSR HTML, hydration payload, `/_server` and `/api/live-power`; prices remain public and live. Verify home access, the 15-minute report expiry and the 30-day signed-cookie path. Test both production hostnames and the isolated PR preview. Earlier apex-only checks do not validate this combined implementation.
3. **Inspect the zone before merging the launch.** Confirm `ldn.house` is an active Cloudflare zone in the deployment account. Check DNS and Workers & Pages → Domains & Routes for `ldn.house` and `www.ldn.house`: no conflicting A/AAAA/CNAME records or custom-domain bindings to another service. Check Page Rules, Single/Bulk Redirects and wildcard Worker routes for apex-to-www loops or rules that intercept these hosts. Review restrictive CAA records if present. Preserve all MX, mail-related TXT and mail-host records; an MX record itself is not a web-route conflict, but an MX target of the apex would need attention before making the apex a web-only Worker origin. Leave Grafana's `dashboard.ldn.house` records, routes and rules alone. Do not create a wildcard route or zone-wide redirect.
4. **Confirm the existing GitHub Actions token's resource scopes.** `CLOUDFLARE_ACCOUNT_ID` must own the zone and Worker. The documented legacy permissions—account Workers Scripts edit and D1 edit, plus zone Workers Routes edit covering `ldn.house`—are sufficient for this custom-domain deployment; no additional DNS edit permission is required for Cloudflare-managed DNS creation. Keep account coverage for creating/deleting PR Workers and D1 databases. Do not replace this with access restricted to the existing production Worker, which would break preview provisioning. If the current secret already has these scopes, no token change is needed.
5. **Merge only when ready to publish.** There is no manual DNS record or redirect rule to create. The production workflow migrates D1 and deploys the three exact custom domains from `wrangler.jsonc`; Cloudflare creates the apex/www DNS records and certificates. The pinned Wrangler 4.127.0 sets `override_existing_origin` and `override_existing_dns_record` in noninteractive runs, so do not rely on CI to stop for conflicts. Recheck step 3 immediately before merging. Do not manually deploy this branch or attach the apex ahead of the privacy decision.
6. **Verify the production workflow and domain activation.** Wait for DNS and TLS activation, then check `https://ldn.house/` serves the app; `https://www.ldn.house/not-a-page?check=launch` returns 301 with `Location: https://ldn.house/not-a-page?check=launch`; the same redirect applies to `/favicon.svg` and `/share.png`; the target missing path returns 404. Confirm the favicon, share image, canonical/meta tags and apex `robots.txt`. Confirm `preview.ldn.house` still serves the app and Grafana's existing hostname still behaves as before. Once apex HTTPS is active, switch Home Assistant’s `rest_command` URL to `https://ldn.house/api/home/address` and confirm successful reports continue. Both hostnames share the Worker and D1, so reporting to preview remains valid during the transition. The [`__Host-ldn-home` cookie is host-only](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#cookie_prefixes): a cookie issued on preview does not transfer to the apex. Visit the apex from home while the report is fresh to obtain its cookie, then verify away access with it and the restricted outsider view without it. Social scrapers cannot fetch the apex share image until launch; check an actual shared link then.
7. **Keep the normal PR-preview lifecycle.** Draft PRs run checks, provision an isolated Worker/database, deploy on `workers.dev`, seed the scrubbed fixture and comment the URL. `previewConfig()` strips every production route and cron trigger. Closing the PR deletes only its preview resources. No preview-workflow or Cloudflare-rule change is needed for the apex.

## Evidence and limits

Read-only checks on 2026-10-19 found no public A, AAAA, CNAME, MX or CAA answers for `ldn.house` or `www.ldn.house`; `preview.ldn.house` and `dashboard.ldn.house` returned Cloudflare A/AAAA answers. Public DNS does not expose the underlying proxied records or prove that zone rules are absent. No production Cloudflare configuration was changed during preparation; the existing Actions workflow deployed only isolated PR-preview resources. A GET of `/zones?name=ldn.house` using the available local Wrangler login returned HTTP 403 / `9109 Invalid access token` (expired login). The GitHub Actions secret cannot be read back. Exact token scopes, private zone records, other custom-domain bindings and redirect/Page Rules therefore remain manual checks, not verified absences.

[Cloudflare's custom-domain guide](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) documents automatic DNS/certificates, the active-zone requirement, CNAME conflicts and exact-host matching. [Workers authorization](https://developers.cloudflare.com/workers/authorization/workers/) requires Worker edit access plus Workers Routes write for each affected zone; legacy permissions continue to work. The [domain attachment API](https://developers.cloudflare.com/api/resources/workers/subresources/domains/methods/update/) lists Workers Scripts write, not DNS write. DNS read and rules read access would help audit conflicts but are distinct from deployment permissions.

The `www` redirect is in the Worker so code, domains and redirect ship together through the existing workflow and can be exercised in local workerd and reviewed in one diff. A Cloudflare redirect rule could avoid Worker invocations, but would add separately managed configuration and permissions. `assets.run_worker_first` ensures static assets also redirect and receive the host-specific indexing policy; this makes asset requests invoke the Worker too. The share card is a static 1200×630 PNG with no live or historical readings; its editable source is `public/share.svg` (`rsvg-convert public/share.svg -o public/share.png`). No Octopus endpoints, polling intervals, retries or cache lifetimes change; both production hostnames share one refresh gate, rather than creating a deployment per hostname.
